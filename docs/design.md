## 0. 定位(Positioning)

**Warranted 要为研究结论补上一种长期缺失的失败信号(failure signal):把"无痕的自我说服(self-persuasion)"变成"有据的定案(settled conclusion)、有痕的变更(traceable change)"。**

它**不是**写作工具、过程账本(work log)、加速器。它**是**一套约束严谨思考的结构:你主张什么、凭什么主张、这层"凭什么"经不经得起复核(review)、每一次变更留不留痕(provenance)。事实与证据可以入图,但它们是这套结构的原料,不是产品的重点。

**工作方式的约束(来自用户访谈)**:

- 人怕麻烦,只在问题足够大时才抬眼细看,所以系统不能指望人来主动把关(gatekeeping)。
- LLM 审查又慢、又贵、结果还不稳定,所以系统不能指望 LLM 来主动把关。
- 结论:把关必须**又便宜又确定**;留痕必须**醒目**,醒目到懒人扫一眼就能看见。

## 1. 本体论(Ontology):一个命题,五个槽位

> 本节取代旧版"3 节点 + 3 角色"模型。旧模型是实践演化途中的中间态,本版是它的逻辑终点。

### 1.1 演化路径(为什么最终塌缩成一个类型)

1. 起点:Toulmin 的 claim / ground / warrant / backing / rebuttal 各自成一种节点类型(node type)。
2. 随后发现,rebuttal 本质上就是方向相反的 ground,于是合并成 statement。
3. 再后来发现,claim 可以充当另一个 claim 的 ground 或 rebuttal,迫使系统为它特判。
4. 再后来发现,warrant 自己也被 backing 支撑、也可以被 rebuttal 攻击——**warrant 同样是命题**。
5. 最后发现,warrant 连节点都算不上,只是命题的一个槽位;ground / backing 退成对证据的两种视角(perspective),claim 退成"有争议"的状态(state)。

五步演化,同一条原则:**角色不是类型**——它们退成状态、视角与槽位(见 §1.3)。

### 1.2 唯一的节点类型:命题(Proposition)

一个命题就是一个可以判定成立与否的陈述,有五个槽位(slot):

| 槽位 | 英文 | 含义 |
| --- | --- | --- |
| 内容 | content | 陈述本身 |
| 证据 | evidence | 附件(文件)或链接(其他命题) |
| 理由 | warrant | 回答"这些证据为什么足以撑起上面的内容";可空,但命题上到 `possibly` 及以上时结构检查要求非空(见 §3.1) |
| 反驳 | rebuttal | 攻击这条命题的命题;可选 |
| 可信度 | qualifier | 单条有序标尺,方向与强度合一:`refuted → unestablished → possibly → probably → certainly` |

**理由(warrant)的两种形态:**

- **内联(inline)**:直接写一段话,放在命题里。它本质上是一条**缺省了证据的命题**——不单独立节点,因而在被晋升之前没有自己的证据、反驳与可信度。
- **晋升(promote)**:把这段理由单独拎出来,立成一条完整命题,原槽位改成指向它。晋升后的理由,就有自己的证据、理由、反驳、可信度。

何时晋升?当要**反驳这条理由本身、给它补依据、或复用同一条理由**时;其余时候留在内联。**攻击一段内联理由时,系统自动把它晋升成命题,再把反驳挂上去**——这步由系统完成,agent 无需额外调工具。晋升出的命题带空理由、落 `unestablished`,合法;它的理由欠账由结构检查自动追讨(§3.1 表注)。

**证据(evidence)只有一个槽,附件和命题都能挂。** 挂到谁的槽上、以谁为中心看,名字就不同:挂到普通命题的证据槽,叫论据(ground);挂到 warrant 的证据槽,叫依据(backing)。backing 是 warrant 的证据,ground 是命题的证据,本质是同一份证据、不同的中心视角;附件与命题在这两个槽里都合法。

**挂进证据槽的命题是引用(指针),不是副本。** 上游看到的就是那条命题当下的 content,不存在"抄一份过来、抄歪了"的可能。这条不变量后面要用两次:它让审查器不必核查证据槽里命题的转述忠实性(§2.2),也让"该重查"可以只盯 (content, qualifier) 两个值传播(§3.1)。

**被推翻的命题也能当证据。** 例如"假设 X 成立"落 `refuted` 之后,它正是"应改用方案 Y"的论据——此时你依赖的不是它的 content 为真,而是"它已被推翻"这件事为真。所以结构检查只排除 `unestablished` 的引用(还没评估的东西撑不起任何结论),不排除 `refuted`(见 §3.1)。代价要认:读图时 `refuted` 节点的 content 语义需要读者自己反转,所以上游的 warrant 应显式写明"因为 X 已被推翻",别让反转留在读者脑子里。

> 旧 `status(proposed/supported/disputed/refuted)` 与 `verification(verified/pending)` 一并**废除**,由 `qualifier` 一条标尺取代;旧 `compile_state` 表**整体废除**——结构检查(structural check)改为每次变更后自动重算(见 §3.1),不再是一个可跑的动作、也不再落库。旧文中的"Statement"就是本节的"命题";"Claim"则是"有争议、需要确立成立与否的命题"。
>
> **"废除 stale"废的是什么**:废的是**落库的 `compile_state` 缓存**——一个会过时、需要显式重跑才能刷新的字段;**保留**的是**派生的过期判定**(§3.1 那套"该重查"警告)。前者是状态,会说谎;后者是每次读取时算出来的函数,不会。所以 §3.1 标题里的"过期"与本处的"废除 stale"不矛盾。

旧状态机各态的去向:`proposed/pending → unestablished`(是否"还没评估",由结构检查区分);`supported → probably/certainly`(强度由 agent 定);`disputed → possibly + 存在正向三档的 rebuttal`(削弱而非推翻,不再单独成态);`refuted → refuted`(须有正向三档的 rebuttal);`verified` → 并入 qualifier 正向档(ground 与 claim 走同一把尺子)。

### 1.3 角色退化为视角(perspective)与状态(state)

旧五角色不再各占一种位置:

- 主张(claim)= **"有争议"这个状态**:命题的成立与否尚未确定、且其裁决会影响后续行动时,它就是主张。
- 论据(ground)/ 依据(backing)= 对证据的两种**视角**(见 §1.2)。
- 推理规则(warrant)= 命题的"理由"**槽位**(见 §1.2)。
- 反驳(rebuttal)= 命题的"反驳"**槽位**(见 §1.2)。

同一条命题,对上当论据、对下当被支撑的主张,角色只取决于以谁为中心看,不取决于节点类型。唯一例外是附件:它是叶子,到此为止,不再需要理由。

### 1.4 关键代价与对策

旧系统里,"类型"还兼着一份**写作引导(writing guidance)**的职责:比如 `create_warrant` 会提示"写领域通用原则,别写 if-then 桥"。塌缩成单一命题 + 五槽位之后,这份引导**由工具的参数描述承担**:content 参数写"可判定的陈述,不写活动流水",warrant 参数写"领域通用原则,不写 if-then 桥";场景特定的写法(如复现 verbatim)进 skill。参数描述负责"这个字段怎么填",工具 description 只放触发与判别,两者不混。

## 2. 认识论分工(Epistemology,已定)

**一个问题只能有一个最终裁决者,而且这个裁决者必须是最接近"事实"的那一层。**

| 层 | 判什么 | 谁 | 确定性 | 当不当门 |
| --- | --- | --- | --- | --- |
| **L1 机械判据** | 结构检查与过期(判据见 §3.1):证据非空、理由非空、附件存在、引用节点的 content/qualifier 有效 | 代码 | ✅ 确定 | **软标红(flag)**(警告+标红);硬仅 V1–V3 输入校验 |
| **L2 审查** | 证据是否支撑命题(文件型:附件支撑;论证型:ground 经 warrant 支撑 claim) | LLM | ⚠️ 可降方差 | **否——只"发现"** |
| **L3 判断** | 综合 ground 与 rebuttal 的力度,给出 `qualifier`(possibly/probably/certainly/refuted…) | **agent + 人** | 人的判断 | 终审 |

### 2.1 compile 的溶解(已定)

`compile` 作为一个统一动作**解散**,拆成三块,各归其位:

1. **结构检查(structural check)** → 归代码:确定性、零语义,每次变更后自动重算、永远最新,没有"stale"、没有"重跑"。具体判据见 §3.1,落地为硬拒绝(V1–V3)加软标红。
2. **LLM 审查** → 按需调用的"第二意见(second opinion)"工具(见 §2.6)。
3. **推进门槛** → qualifier 变更时的软标红(警告+标红,不拦截,见 §3.1)。

于是,旧系统"stale → 重跑 compile → 改 → 再 compile"的循环被**结构性取消**:没有需要反复跑的 compile,只有自动刷新的状态和可选调用的第二意见。

### 2.2 审查器契约:两个问题(已定)

审查器(第二意见)只回答两个问题;只要答"否",就必须指出**具体的断点(broken point)**并**给出引证(citation)**:

**范围(scope)**:review 的输入是**单条命题**,视野是它自己 + 它的直接证据 + 它的 warrant(内联或晋升后的)。不递归、不吃子图。

| 问题 | 内容 | 只针对 |
| --- | --- | --- |
| **Q1 忠实性(faithfulness)** | 证据有没有**真的说**命题声称的事(还是捏造、误读或直接矛盾) | **附件型证据** |
| **Q2 有效性(validity)** | 证据**即便为真**,是否真的推出命题(推理有没有接上) | 整条命题的推理 |

- **命题型证据不查 Q1。** 理由:挂进证据槽的命题是**引用**,不是副本(§1.2)——审查器、上游 agent、人看到的是同一份 content,不存在"转述失真"这种可查的失真。它的真伪不由审查器**递归**核查,它只查"这批 ground 经这条 warrant 能否推出 claim"。
- **前提的极性是前提的一部分。** 自 `refuted` 命题也能当证据(§1.2)起,"默认 ground 为真"这句话不再自足:一条 content 写着"假设 X 成立"、qualifier 落 `refuted` 的证据,把它的 content 当真恰恰是反的。所以递给审查器的每条命题型证据都带 **(content, qualifier)**,Q2 问的是"以这些证据**当下的认识状态**为前提,这条 warrant 能否推出 content"。
- **但审查器不收被审查命题自己的 qualifier。** 那是 L3 的结论,递过去就是把答案递给它。边界的准确表述是:**引用节点的 qualifier 进,被审查命题自己的 qualifier 不进**——检查点在 prompt 构建函数的入参类型,越界的修法是删字段,不是在 prompt 里加禁令。
- 于是混合证据(附件与命题同时在槽里)不需要额外规则:Q1 扫附件,Q2 扫整条推理,命题型证据带着自己的极性作为 Q2 的前提出现。
- **反模式(anti-pattern)**(循环论证 / if-then 桥 / 因果混淆 / 无关内容)**不再是合同条款**,降级为 prompt 里的"识别辅助"——帮审查器认出 Q2 断链的常见形态,但合同只有 Q1/Q2 两条。这样既抓得到清单外的新形态,方差也更低。

**一条 finding 的构成(合同的产出侧)**

审查器答"否"时产出一条 finding。它由三部分构成,缺一不可:**是哪个问题断了**(Q1 / Q2)、**断在哪**(引证)、**怎么断的**(断点陈述)。

**引证是字段,不是措辞。** §2.3 的"强制引证"若只写在 prompt 里,就会有时遵守、有时不遵守,且没人能机械看出差别。它必须是 schema 里的必填项,并尽可能落到**可机械校验**的部分:

| 问题 | 引什么 | 机器能验什么 |
| --- | --- | --- |
| **Q1** | 附件原文(路径 + 定位 + 逐字片段) | 路径必须 ∈ 本命题的附件槽。片段是否真在该处,机器验不了,留给人 |
| **Q2** | **图内文本**:本命题的 content / warrant,或某条证据命题的 content(节点 + 槽位 + 逐字片段) | 片段必须是该槽位内容的**逐字子串**;验不过 = 审查器在编 |

Q2 引图内文本不是凑数。Q2 断在推理里,**没有外部原文可引**,而它的全部价值在于指出**具体**断点——"具体"的唯一操作化定义就是能指到具体的字。一条说不出"是 warrant 的哪句话跨不过去"的 Q2 finding,已经退化成"我觉得推理不够严密",那正是 §2.4 要挡的误拒来源。

由此,`question` 唯一决定引证形态,做成判别联合(discriminated union)后 **"Q1 只针对附件型证据"从一句措辞变成类型层面无法违反**——与 §2.2 输入边界同一条修法:越界的修法是改类型,不是在 prompt 里加禁令。

**审查器只报把握度,不报严重度。** finding 带 `confidence`(我这条判断有多大把握),**不带 `severity`(这个问题对结论有多严重)**。判据是一句话:**这个字段的答案需不需要看到局部之外?** 需要 → 不该在 finding 里。severity 需要(审查器不递归、不吃子图,不知道这条命题在整张图里承担什么);confidence 不需要,它是审查器对自己输出的元判断,是它唯一有资格说的东西。`confidence` 同时是 §2.4"拿不准的给提示"的落点,不必另开一个 hint 通道。取值只有 `high` / `low` 两档——三档的中间档是垃圾桶,拿不准的会全滑进去,于是三档退化成"high 和其他"。

**finding 不带的东西**(每条都对应一条已定原则):

- ❌ **修改建议**:"该怎么改"是 L3 的活;带建议的 finding 会诱导 agent 照做,把顾问变成事实上的门。
- ❌ **严重度**:见上。
- ❌ **状态字段**(pending / dismissed):状态不落在 finding 上。"已阅"由事件流里有没有对应 id 的 `dismiss` 事件算出来(§3.1b),与警告一致、零可变状态。在 findings 表上加一列 `status` 就破了 I8 的"永不更新"。
- ❌ **反模式分类**:已降级为 prompt 识别辅助,做成字段就是把它升回合同。

**答"是"也要留痕。** review 事件记录每个问题的结论:`pass` / `fail` / `n/a`。`n/a` 专给"该命题没有附件型证据、Q1 无所施力"——记成 `pass` 会造出"忠实性已核实"的假象。没有这一层,"从没 review 过"与"review 过且没问题"在图上分不开,而这两者对 agent 的意义完全不同。

结构定义见 `docs/api.md` §4.1。

### 2.3 审查器的去随机化(压方差,不归零)

审查器是**顾问(advisor)而非门(gate)**,"真读证据"优先于"零方差"。据此:

- 审查调用固定 `temperature=0`,钉死模型与 prompt 版本,协议 hash 写入持久化记录。
- **审查器可带只读工具**(Read/Glob/Grep),落地到实际文件;每条 finding 强制**引证原文**,让阅读可审计。
- 方差靠"温度 + pin + 引证 + 只问 Q1/Q2"压到最低,但不追求归零(顾问允许两次结论略有出入)。

### 2.4 错误不对称

对于"非终审的前置过滤器",误拒(false rejection)(把还不错的论证判成 fail → 循环、烧钱、信任崩塌)比误放(false acceptance)(漏掉一个细微缺陷 → 人/agent 在 L3 仍会发现)更贵。所以 L2 要**高精度、低召回(high precision, low recall)**:只抓抓得准的语义缺陷,拿不准的给提示或交 L3。

### 2.5 发现(findings)的处置(已定)

> 一条 finding 由什么构成、为什么引证必须是字段、为什么不带严重度,见 §2.2 末尾"一条 finding 的构成";结构定义见 `docs/api.md` §4.1。本节只管它产出之后怎么办。

- **持久化到图**,与命题绑定。
- **仅高亮可见,不拦截**:所有图读取接口对"有未处理 finding 的命题"给出醒目标记(接口清单见 `docs/api.md`;旧 `list_claims` 随"claim 是状态不是类型"一并失去所指);可视化中显示红点(red dot)/徽标(badge);qualifier 落到非 `unestablished` 时若仍有未处理 finding,返回醒目 warning。
- 本质:**改变"显示什么",不改变"允许什么"**——不 fail、不打断、零方差、不烧钱,但让语义缺陷无处隐形。
- **"未处理"的唯一出口是 `dismiss`(§3.1b)或一次新的 `review`**。finding 与结构检查警告共用 dismiss 这个动作,但**不跟着图变化自动过期**——理由见 §3.1b 那张对照表。

### 2.6 第二意见(Second Opinion,已定)

原 compile 的 LLM 审查,重新定位为**按需调用的第二意见**,只有一个通道:

| 通道 | 发起 | 机制 | 产出 |
| --- | --- | --- | --- |
| `review` | agent 想独立确认时 | 第三方 LLM agent(独立审查器)按 **Q1/Q2** 查局部证据 | 带引证的 findings 落库 |

- **触发**:按需,系统不逼。它带只读工具真读文件,所以慢且贵——这不违反 §0 的"把关要廉价":廉价确定的那道是结构检查,review 从来不是门。
- **独立性**:LLM 审查器与主 agent 的推理相互隔离(独立子进程/subagent,不共享上下文)。
- **命名**:动词 `compile` **退役**(它暗示"要跑的动作 + 过/不过的门",而这两者都已不存在),`review` 是它唯一的继承者。
- **人类背书/质疑不单设通道**:人直接改图就是一次带归因的写操作,已由 I8 留痕(见 §3.1c),不需要 `confirm`。

## 3. 契约(Contract,已定)

**归属**:结构检查与过期(§3.1)/ 处置警告 dismiss(§3.1b)/ 留痕 I8(§3.1c)/ 判断归人 J(§3.2)/ 场景约定 C(§3.3)。

> **工具面契约不在本文档**——哪些工具存在、各自的参数与调用形态(含"攻击内联 warrant 触发自动晋升"用什么 API 表达、21 个旧工具各自的去向),见 `docs/api.md`。本节只定义机器必须执行的判据,不定义调用它的接口。

### 3.1 结构检查与过期(统一机制)

**姿态原则(posture,用户定)**:系统**从不拒绝认识论写入**,只警告+标红;agent 拥有完全的自由。只有数据不合法才拒绝写入。整个系统是"镜子(mirror)",不是"裁判(judge)"。**这条原则零例外**——曾短暂存在的 V4(warrant 写入期必填)已取消,理由见下表注。

**原理(归纳,无特例)**

- 附件是叶子,只按"文件内容"判定变没变。
- 每个命题对外只暴露 **(content, qualifier)** 两样;只有它们变了,才可能影响上游。
- 一个命题被重查,只因为:① 自己变了(content、warrant 文本、证据成员清单、反驳成员清单任一变化);② 它直接引用的节点(证据、反驳、或晋升后的 warrant)的 (content, qualifier) 变了。qualifier 自身变化不触发重查,是重查的产物。
- 重查后 content、qualifier 都不变,则链条在此截断,上游无感;变了,才继续往上冒。
- warrant 晋升 = 新命题诞生 = 该命题自身的结构检查启动,不额外触发原命题。

**结构检查判据(每个命题按自己状态)**

> **warrant 非空是表内判据,不是入场券。** 它曾被设计成写入期硬拒(V4),已取消。理由是类型错误:本表的逻辑是"你要多确信,就交多少结构成本",而 warrant 完全符合这个梯度,把它拎出来当入场券把一条梯度化要求做成了门。放回表里之后它与"证据非空""附件存在"同构——三条都是零语义的槽位检查。
>
> 附带收获两项:①`unestablished` 的记录性命题("某文献声称 X")与中间态命题不必先编一句理由才能落库,归纳期的摩擦消失在它本该消失的地方;② §1.2 的"攻击内联理由触发自动晋升"不再与硬拒相撞——系统建出的理由命题带空 warrant + `unestablished` 落库完全合法,而它的理由欠账由**已有判据**自动追讨(上游要上 `probably` 就得让它 ≠ `unestablished`,判档时又撞上 warrant 非空),不需要任何新机制。
>
> **代价要认**:一条空 warrant、`unestablished` 的命题可以支撑一条 `possibly` 结论且全程不标红。分界线是"你说有可能,你自己得说出凭什么;你引用的东西可以还没论证"——这是 possibly 放宽的既有代价的延伸,不是新增口子。实现侧代价:warrant 字段可空,读取路径须处理空值。

| 状态 | 检查"支撑侧" | 检查"攻击侧" |
| --- | --- | --- |
| 有可能(possibly) | ① 证据非空;② 附件文件存在;③ **理由非空** | 不查 |
| 很可能 / 确信(probably / certainly) | ① 证据非空;② 附件文件存在;③ **理由非空**;④ 每条直接引用的命题存在、content 未变、qualifier ≠ `unestablished` | 不查 |
| 被推翻(refuted) | 不查 | 反驳槽至少一条,且每条反驳存在、content 未变、qualifier 落正向三档 |
| 未评估(unestablished) | 不查 | 不查 |

> **为什么 possibly 单独放宽**:`possibly` 的语义本就是"证据不足到只能说有可能",再要求它的引用链全部可用,会让大量诚实的弱结论常亮标红——标红一旦常亮就贬值。所以 possibly 只查"你至少挂了证据、说了句凭什么、挂的文件还在",不查引用链的可信度。引用链检查的实质起点在 `probably`。
>
> **为什么支撑侧放宽到 `≠ unestablished`、攻击侧仍要正向三档**:这不是遗漏,是不对称。证据槽引用一条 `refuted` 命题时,你用的是"它被推翻"这个事实(§1.2);反驳槽引用一条 `refuted` 的反驳时,你用的是它的攻击力,而攻击力随它自己被推翻一起消解了。
>
> **放宽之后闸门为什么还够用**:两件事分工。**闸**(`≠ unestablished`)只问"这条证据能不能用"——还没评估的东西撑不起任何结论,`refuted` 能撑(以"它被推翻"的形式)。**极性变了没有**不由闸管,由 §3.1c 的基线比对管:证据从 `certainly` 掉到 `refuted` 是一次 qualifier 变化,照样触发"该重查"并标出触发点。所以闸不必再区分正负,否则就是同一件事在两个地方各判一次、迟早判出两个答案。
>
> 正向命题带着正向三档的反驳,**不标红**——反驳的可信度不等于打击力度,力度综合判断归 L3(见 §3.2)。反驳在图里本来可见,系统只照它存在,不替人算它多狠。
>
> **上表按档分,重查不按档分。** 两者问的不是一个问题:表问"以你现在这个档位,结构上该有的东西齐不齐",重查问"你当初据以判档的那些东西,还是不是那个样子"。后者与档位高低无关,所以它对每一条判过档的命题一视同仁地跑——`refuted` 的支撑侧在表里不查(它的成立不再靠证据),但它判 `refuted` 时依据的反驳被删掉或被改判,照样标红;`possibly` 在表里不查引用链可信度(闸从 `probably` 起),但它引用的证据从 `certainly` 掉到 `refuted` 仍是一次要重看的变化。唯一不跑重查的是 `unestablished`:它从没判过,没有基线可比——是无从比较,不是被豁免。

**归属**

- 系统只做:发现"该重查"(零语义、零成本),并**标出触发点(trigger)**(哪个证据掉出可用档位、哪条 content 变了、哪个附件不见了),以警告/标红/建议呈现。
- 每条警告除触发点外还须带一个**稳定 id**,从 `(node_id, 判据编号, 触发点, 重查指纹)` 派生;重查指纹的字段清单就是上面"原理"的两条触发条件。这是 dismiss 能指名驳回的前提(§3.1b),而且让复燃变成 id 派生的自动结果——不设可变的警告状态表,`dismiss` 因此保持为一条纯 append 事件。派生式与读取算法见 `docs/api.md` §5。
- agent / 人做:真正的重查——读证据、判断理由是否撑得住、决定 content / qualifier 改不改、并落地修改。
- 系统不替查、不替改、不下结论;只照,不推。

**硬拒绝(数据不合法,拒绝写入)**

| 编号 | 校验 |
| --- | --- |
| V1 | content 非空 |
| V2 | 引用指向存在的节点,不产生悬空引用 |
| V3 | 写入时附件路径存在 |

> **三条全是数据合法性,没有一条是认识论要求**——姿态原则因此字面成立、零例外。原 V4(warrant 非空)已移入结构检查表(见上)。

> 原"`source=literature` 必须带附件"随 `source` 字段一并删除;"引用了就必须附上原文"改由结构检查(证据非空、附件存在)+ Q1(审查器查真伪)+ persona 约定共同承载。附件"写硬读软":写入时路径必须存在(V3),写入后文件被删在读时标红。
>
> **附件还查一条"是否仍在项目根内"**(根 = 数据库文件的祖父目录,也就是审查子进程实际的 cwd)。路径存在但解析到根外——绝对路径、`../` 指出去、文件被移走——同样标红,不升级为硬拒:写入那一刻的合法性 V3 已经查过(文件确实在),而"在不在根内"决定的是这份论证换台机器、换个人还能不能复现,是随时间漂移的性质,与文件被删同类,因此同归读时标红。两者互斥上报——文件都不在了,再补一句"它不可移植"是噪音。解析基准由 V3 与读时检查共用同一处计算:两边各算一次,迟早出现"写得进、读出来标红"的分裂。


### 3.1b 处置警告与意见(dismiss)

系统标出的"该重查"警告、审查器给出的 finding,agent 看完都可以**驳回(dismiss)**,判定它不成立或无需处理。**两类对象共用一个动作**——它们要 agent 做的事是同一件:看一眼,判一次,留个理由。

- **作用域是单条**:每条警告 / finding 有自己的 id,驳回一条只降级一条。**不提供命题级批量驳回**——批量会让"没看就驳回"变便宜,而驳回的全部审计价值就靠它贵。(按 id 逐条、每条自带理由的批量调用不在此限:它省的是往返,不是思考。)
- **驳回必写理由**:至少一句"为什么认为没问题",让"没看就驳回"变得有成本、可审计。不设长度下限——下限可以刷,刷起来比写一句真话便宜,只会给审计一种虚假的确定感;真正让它贵的是它进事件流、可被逐条读出来。
- **驳回是降级不是删除**:降为"已阅(acknowledged)",留痕(时间 + 理由),不再常亮、可查——行使 L3 判断权是正常动作,不是遮丑。

**两类对象的过期语义相反,这是有意的:**

| | 复燃 |
| --- | --- |
| **结构检查警告** | **自动**。判据与重查触发条件是同一套:① 本命题的 content / warrant 文本 / 证据成员清单 / 反驳成员清单任一变化;② 直接引用节点的 (content, qualifier) 变化。任一发生,该命题上所有"已阅"警告一律复燃。一套判据两处用,不另立窄口径——两套判据迟早会漂移成两种语义。落地上这一条不需要单独实现:判据即警告 id 的重查指纹(见上"归属"),指纹一变 id 全变,旧的 dismiss 事件自然匹配不上 |
| **审查 finding** | **不自动过期**。只能被"驳回并写理由"或"新一次 `review` 取代"结算 |

差别的根据:警告是从当前状态**算出来**的,所以它永远说的是现在;finding 是一条历史意见,算不出来。若让 finding 随指纹变化自动失效,改一个逗号就能清掉一条"你的论据推不出结论"——那是一条洗白通道,正是 §0 要消灭的东西。

### 3.1c 留痕契约(I8,已定)

append-only 事件流(event log),**在写事务内同步写入,永不更新、永不删除**,是过期检测、变更复核、`review`/`dismiss` 落库的共同数据源:

| 项 | 契约 |
| --- | --- |
| 节点变更 | op ∈ {create, update, delete};update 存**字段级 diff** `{field: old → new}`;delete 存**整节点 before 快照(snapshot)**(墓碑(tombstone)即此记录,不设归档表/软删标记) |
| 归因(attribution) | 每条带 `at`(时间戳)+ `by`(`tool` / `human` / `system`)。**`human` 目前无入口**:visualizer 对图只读,人只能经 agent 改图,所以在写入通道落地前(§5.1,优先级低)`by` 实际只产出 `tool` 与 `system`,人的意图靠 `note` 记录("用户要求改成……") |
| 动机(motive) | 可选 `note`,agent 写了就记;变更影响已定案命题时,工具温和提示"建议留 note 说明什么证据逼的" |
| 意见事件 | `review`(第三方 agent 的 findings)/ `dismiss`(对警告或 finding 的驳回,§3.1b)入同一事件流,供过期检测与"已阅"判定使用 |
| 派生关系 | 设 qualifier 时**同步快照**每个直接引用节点的 `(content hash, qualifier)`,作为该次判断的**基线(baseline)**;过期检测 = 拿引用节点的当前值与基线比。基线随 qualifier 写入事件一起落库,不从历史回放重建。**"只有一个写入者"是接口面的硬约束**:新建命题一律落 `unestablished`,不接受 qualifier 入参,改 content 的工具也不接受——只有"设 qualifier"这一个动作能写基线(见 `docs/api.md` §2.1/§2.3) |

> **为什么存基线而不从 I8 回放重建**:I8 只存本节点的字段级 diff,要回答"设 qualifier 那一刻,被引用节点 X 的 content 是什么",必须回放 X 的完整 diff 历史——O(历史长度),且实现复杂。快照是 O(引用数) 的空间换 O(1) 的查询。
>
> **代价要认**:这是一份缓存,早期版本"无缓存状态"的说法据此作废。它与旧 `compile_state` 的区别在于**只有一个写入者**:基线只随"设 qualifier"这一个动作更新,没有第二条路径能改它,所以不会像旧 `compile_state` 那样漂移成一份需要显式重跑才能刷新的谎话。
>
> 附带效果:content"改了又改回来"比 hash 相等,判为**未变**(比"看有没有发生过写事件"更贴近本意)。

## 6. 决策记录(Decision Log)

### 已定
- **定位**:把关要廉价且确定,留痕要显眼(人懒,只看大问题)。
- **本体**:一个命题 + 五个槽位(content / evidence / warrant / rebuttal / qualifier);warrant 是"理由"槽位,可内联、可晋升;ground / backing 退成对证据的两种视角,claim 退成"有争议"状态;**无"公理"概念**;Qualifier 单条有序标尺 `refuted → unestablished → possibly → probably → certainly`。
- **tags 体系废除**:不引入分类轴或 taxonomy。旧 tag(namespace / 基数 / 相似度 / rename / merge / claim_id)及其数据表全部废除——它服务的"图太大、上下文塞不下、需便宜索引分批"的场景已随上下文容量消失;归纳期的"按主题取一批"用关键词检索 + agent 迭代解决;跨会话分类不做在本系统内。**本条推翻 0.5.0 已定案的"图规模原语全进 + 筛选下放"**——那套设计的前提(上下文装不下)不再成立,不是实现方式变了,是问题消失了。
- **结构检查与过期(统一机制)**:`unestablished` 不查;`possibly` 查"证据非空 + 附件存在 + 理由非空";`probably/certainly` 另加"引用的命题存在、content 未变、qualifier ≠ unestablished";`refuted` 查"反驳槽非空且反驳落正向三档"。过期靠归纳——附件是叶子、命题对外只暴露 (content, qualifier)、逐层自动传播,不全图重跑。
- **硬拒绝 V1–V3**:content 非空、引用不悬空、写入时附件路径存在。三条全是数据合法性,姿态原则("从不拒绝认识论写入")**零例外**。
- **V4(warrant 写入期必填)已取消**:它把一条梯度化的结构要求做成了入场券,是类型错误;warrant 非空移入结构检查表的 `possibly` 及以上,与"证据非空""附件存在"同构。收益:`unestablished` 的记录性/中间态命题不必先编理由才能落库;§1.2 的自动晋升不再与硬拒相撞,晋升出的空理由命题的欠账由已有判据自动追讨(上游要 `probably` 就得让它 ≠ `unestablished`,判档时撞上理由非空),不需要新机制。代价:空理由 + `unestablished` 的命题可以支撑一条 `possibly` 结论而全程不标红;实现侧 warrant 字段可空。
- **refuted 可作证据**:支撑侧的闸放宽到 `qualifier ≠ unestablished`,`refuted` 命题能当论据用(用的是"它被推翻"这个事实);攻击侧不跟着放宽,反驳仍须落正向三档(攻击力随被推翻而消解)。极性翻转不由闸管,由基线比对抓。
- **归属**:系统只发现"该重查"并标出触发点,不替查、不替改、不下结论;重查归 agent / 人。
- **dismiss**:作用域是**单条**警告或 finding(不提供命题级批量,批量会让"没看就驳回"变便宜;按 id 逐条、每条自带理由的批量调用不在此限);必写理由、不设长度下限;降级留痕(已阅);**结构检查警告自动复燃**(判据与重查触发条件同一套,不另立窄口径),**finding 不自动过期**(只能驳回或被新一次 review 取代——警告能重算所以说的是现在,finding 是历史意见,让它随指纹自动失效就是一条改逗号洗白的通道);**confirm 废除**(人直接改图即留痕)。
- **警告可寻址**:每条警告带从 `(node_id, 判据, 触发点, 重查指纹)` 派生的稳定 id,指纹字段清单即重查触发条件。dismiss 靠它指名;复燃靠它免费得到——不设可变的警告状态表,dismiss 保持为纯 append 事件。
- **认识论**:L1 机械判据是软标红(硬仅 V1–V3);L2 审查只发现、不裁决;L3 判断归 agent/人;**compile 动词退役**,`review` 是唯一继承者;findings 持久化 + 仅高亮可见;误拒 > 误放。
- **审查器契约**:两个问题——**Q1 忠实性**(只针对附件型证据)+ **Q2 有效性**(整条推理);输入是**单条命题** + 直接证据 + warrant,不递归、不吃子图;命题型证据是引用不是副本,故不查转述忠实性;**引用节点的 qualifier 进、被审查命题自己的 qualifier 不进**(前提的极性是前提的一部分,自己的档位是待判的结论);反模式降为 prompt 识别辅助;审查器**可带只读工具**,temp=0 / pin / 强制引证压方差。
- **finding 的构成**:`question`(Q1/Q2)+ 断点陈述 + **必填引证** + `confidence`。**引证是字段不是措辞**,且尽量落到可机械校验的部分:Q1 引附件(路径须在附件槽),Q2 引**图内文本**(逐字片段须是被引槽位的子串——验不过即审查器在编)。`question` 唯一决定引证形态,做成判别联合后"Q1 只针对附件"在类型层面无法违反。**只报 `confidence` 不报 `severity`**,判据是"这个字段的答案需不需要看到局部之外"。不带修改建议、不带状态字段、不带反模式分类。答"是"也留痕:review 事件记 `pass`/`fail`/`n/a`,`n/a` 专给"没有附件、Q1 无所施力"。
- **结算**:停止准则**不设**;`get_stats` 出结算摘要(未处理 finding、结构检查违反、待重查警告);review 仅 persona 惯例,无系统提醒。
- **留痕契约(I8)**:append-only 事件流(事务内同步写);update 存字段级 diff、delete 存整节点 before 快照(墓碑即历史记录,硬删);每条带 `at` + `by`(`tool`/`human`/`system`,`human` 待 visualizer 写入通道);动机为可选 `note`;`review`/`dismiss` 入同一事件流。
- **基线存快照,不回放重建**:设 qualifier 时同步快照每个引用节点的 `(content hash, qualifier)`。这是一份有意保留的缓存(早期"无缓存状态"的说法作废),安全性来自**只有一个写入者**——这一条在接口面上兑现为"新建命题不接受 qualifier 入参、改内容的工具也不接受",否则第二个写入者会让基线退化成旧 `compile_state` 那种需要显式重跑才能刷新的谎话;附带效果是 content 改回原样判为未变。
- **交付形态**:就地重写本仓库插件(不迁移到外部平台);**工具面契约另立 `docs/api.md`**,本文档只定义判据不定义接口;**旧库断代只读归档,不写 migration**(status→qualifier 的映射需语义判断,机械迁移会造出"没人判过却有档位"的命题)。
